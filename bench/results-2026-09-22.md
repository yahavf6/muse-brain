# Bench results, 2026-09-22

Measures synthetic decision graphs written through the real `log` verb (zod validation, `BEGIN IMMEDIATE`, content hash, FTS triggers, edge triggers, and the reply footer), plus `ask`/`search`/`context`/`get` latency and hook overhead, at increasing graph size. This run includes the `action_open` index fix (commit e2d1237) and the Jev-off early return in `jevLinkSuggestions`. Reproduce with `npm run bench` (default sizes 1,000 / 10,000 / 100,000); add `BENCH_SIZES=1000,10000,100000,1000000 npm run bench` to include 1M, expect it to take hours.

**Machine:** Apple M4 Pro, 48 GB, macOS 26.6.2, Node 24.11.1, 2026-09-22, Jev: off

## Reading the numbers

- Jev was off for this run (`BRAIN_JEV=off`, no `TYPESAFE_API_KEY`), so there was no network round trip anywhere, and `jevLinkSuggestions` (`src/verbs.ts`) returns `[]` immediately instead of running its FTS `bm25` candidate query, so `log` p50 no longer climbs with size (0.171 ms to 0.175 ms from 1,000 to 100,000 rows). With a key present, `log` adds one Jev call budgeted at 1.5 s for link suggestions, and `ask` adds one budgeted at 2.5 s for intent classification and relevance ranking; neither round trip is reflected in these numbers.
- The remaining per-write cost in `log()` is zod validation, the `BEGIN IMMEDIATE` transaction, the content-hash dedupe lookup, FTS5 index maintenance (the `node_fts` triggers), and the indexed outcome-gate lookup (`action_open`, via `footer()`): all flat operations, which is why `log` p50 and p95 barely move across three orders of magnitude.
- `context` (a 2-hop recursive CTE over the edge table) and `get` (by id) stay flat across all three sizes because both are index walks from a known starting point, not scans.
- 1,000,000 was not run to completion in this session, for time reasons; the script supports it via `BENCH_SIZES`.
